## 将 ToolExecutor 替换为 McpClientBridge（复用 MCP Server）

之前的方案将 MCP Server 的工具逻辑在 ToolExecutor.ts 中重新实现了一遍。改为通过 MCP Client 直接连接到已有的 MCP Server，避免维护两份代码。

### 改造内容
- **删除**: `src/electron/main/ToolExecutor.ts`（不再需要，所有工具逻辑统一在 MCP Server 中）
- **新增**: `src/electron/main/McpClientBridge.ts` - MCP Client，通过 stdio 子进程连接到 `dist/electron/mcp/McpServer.js`
  - `connect()`: 启动 MCP Server 子进程并通过 MCP 协议握手
  - `getToolDefinitions()`: 从 MCP Server `listTools()` 获取工具列表，转换为 OpenAI Function Calling 格式
  - `executeTool()`: 通过 `client.callTool()` 执行工具
  - `getToolDescriptions()`: 获取工具名称+描述（供 PromptBuilder 动态构建提示词）
- **修改**: `BaseAIService.ts` - `import` 从 `ToolExecutor` 改为 `McpClientBridge`（接口完全兼容）
- **修改**: `PromptBuilder.ts` - 工具列表从硬编码改为调用 `getToolDescriptions()` 动态获取
- **修改**: `main.ts` - 在 `app.whenReady()` 中调用 `ensureMcpConnected()` 启动 MCP 连接；在 `window-all-closed` 时断开

### 优势
- 工具定义和实现只在 `McpServer.ts` 维护一份
- MCP Server 新增工具后，AI 助手自动可用
- 通过 MCP 协议标准化通信，架构更清晰

## 修复打包后 MCP 工具不可用的问题（asarUnpack 方案）

### 问题
McpClientBridge 通过 `StdioClientTransport` 启动 `node dist/electron/mcp/McpServer.js` 子进程来连接 MCP Server。打包后（electron-builder, asar: true）：
1. `process.cwd()` 不再指向项目目录
2. `dist/` 文件被打包进 `app.asar`，`node` 子进程无法执行 asar 内的 JS 文件
3. 导致 AI 助手的工具调用功能在打包后完全不可用

### 方案演变
先尝试了 InMemoryTransport 方案（进程内通信），后改为更简洁的 **asarUnpack 方案**，保持 stdio 子进程方式不变，复用一套逻辑。

### 最终方案：asarUnpack（排除 asar + 路径修复）
将 McpServer.js 及其依赖文件通过 `asarUnpack` 配置排除出 asar，打包后这些文件会被释放到 `app.asar.unpacked/` 目录下，node 子进程可以正常执行。

### 改动
- **修改** `electron-builder.yml`
  - 新增 `asarUnpack` 配置，排除 `dist/electron/mcp/**/*`、`dist/electron/main/**/*`、`dist/types/**/*`、`dist/constants/**/*`
  - McpServer.js 的完整依赖链涉及 11 个本地模块，全部需要排除
- **修改** `src/electron/main/McpClientBridge.ts`
  - 保持 `StdioClientTransport` 子进程方式
  - 新增 `getMcpServerPath()` 函数，根据 `app.isPackaged` 判断环境：
    - 开发模式：`process.cwd()/dist/electron/mcp/McpServer.js`
    - 打包后：`app.getAppPath().replace('app.asar', 'app.asar.unpacked')/dist/electron/mcp/McpServer.js`
  - 新增路径存在性检查
- **还原** `src/electron/mcp/McpServer.ts` — 恢复原始 stdio 直接启动方式
- **删除** `src/electron/main/InMemoryTransport.ts`（不再需要）

### McpServer.js 完整依赖链（11 个本地模块）
编译后均在 dist/ 下，全部需要通过 asarUnpack 排除：

## MCP 连接稳定性加固 & 自动降级

### 问题
打包后 `process.execPath` 是 Electron 的 exe 文件（如 `MHAtomExcelTool.exe`），不是 Node.js，导致 `StdioClientTransport` 启动 MCP Server 子进程失败。

### 修复方案

#### 1. 修复 `process.execPath` 问题 (`McpClientBridge.ts`)
新增 `getNodeExecutable()` 函数，智能查找 Node.js 可执行文件。

**关键发现**：即使在开发模式下，`electron.exe` 启动纯 Node 脚本时也会初始化 GPU 进程等 Electron 组件，
产生额外的 stderr 输出，干扰 MCP 的 stdio JSON-RPC 通信，导致协议握手永远无法完成。
因此**开发模式和打包模式都必须使用系统 node**，不能用 `process.execPath`。

查找优先级（统一逻辑，不再区分开发/打包）：
  1. 系统 PATH 中的 `node`（通过 `where node` / `which node`）
  2. 常见安装路径（Program Files/nodejs, nvm-windows 等）
  3. 回退到 `process.execPath`（给出警告日志，大概率失败）

#### 2. 添加重试机制 (`McpClientBridge.ts`)
- `connect()` 方法支持 `maxRetries` 参数（默认 3 次）
- 重试间隔递增（1s → 2s → 3s）
- 每次重试前清理上次失败的连接资源
- 新增 `lastError` 字段和 `getLastError()` 方法供外部查询

#### 3. 自动降级为纯 AI 问答 (`BaseAIService.ts`)
- `getTools()` 方法在每次调用时检查 `getMcpClientBridge().isConnected()`
- MCP 未连接时返回空数组 → AI 服务不会发送 `tools` 参数 → 纯文本问答模式
- 降级是透明的，不影响 AI 助手的基本问答功能

## 修复 DeepSeek API 输入长度超限（400 Bad Request）

### 问题
系统提示词中嵌入了 435 个原子的**完整元数据**（包含每个原子的所有参数定义、类型、可选值等），导致：
- System prompt 长度: 182,248 chars（约 55,425 tokens）
- 加上对话历史，总输入 token 达到 286,745
- 远超 DeepSeek API 的 98,304 token 限制
- 报错: `Input length 286745 exceeds the maximum length 98304`

### 修复方案

#### 1. 精简系统提示词 (`PromptBuilder.ts`)
- **之前**: `buildAtomSummary()` 为每个原子生成完整的参数信息（funcName、displayName、className、baseClass、signature、说明、用法、每个参数的类型/可选值等）
- **之后**: 只生成按 `baseClass` 分组的精简索引，每组仅列出 funcName 列表
- 效果: system prompt 从 **182,248 chars → 12,683 chars**（降低 93%），tokens 从 **55,425 → 3,717**
- AI 需要具体参数信息时，通过 `search_atom_metadata` MCP 工具按需查询

#### 2. 对话历史自动裁剪 (`BaseAIService.ts`)
- 新增 `trimHistoryIfNeeded(maxTokens)` 方法
- 在 `chatStream()` 每次发送 API 前自动检查 token 估算值
- 裁剪策略：保留 system 消息 + 最近对话，从最早的历史消息开始移除
- 保持 tool 消息和关联的 assistant tool_calls 消息的完整性

#### 3. 修复 Token 估算严重偏低导致裁剪不生效（二次修复）
精简提示词后仍然超限（115,112 > 98,304），因为 token 估算有三个漏洞：

**问题 1**: `estimateTokens` 公式太乐观
- 之前：英文 4 字符/token、中文 1.5 字符/token
- 之后：英文/JSON 2.5 字符/token、中文 1.2 字符/token（更接近真实 BPE tokenizer）

**问题 2**: `estimateMessagesTokens` 没有计算 `tool_calls` 中的函数参数
- assistant 消息的 `content` 可能为 `null`，但 `tool_calls` 里有大量函数名和参数 JSON
- 修复：遍历 `tool_calls`，加上 `function.name` + `function.arguments` 的 token 估算

**问题 3**: tools 定义本身未纳入预算
- 9 个 MCP 工具的 JSON schema 每次 API 调用都会发送，占用大量 token
- 修复：新增 `estimateToolsTokens(tools)` 函数
- `chatStream()` 中的安全阈值从固定 80,000 改为 `90,000 - toolsTokens`（动态扣除）

#### 4. 修复多轮工具调用 token 持续膨胀（三次修复）
仍然报 `Input length 116164 exceeds the maximum length 98304`，根因是**多轮工具调用循环中 token 持续增长**：

**问题 1**: 裁剪只在第一次 API 调用前执行
- 工具调用循环中每轮都会追加 assistant tool_calls 消息 + tool 结果消息
- 工具结果可能非常大（如 `read_excel_workbook` 返回 39 万字符的 Excel 数据）
- 后续轮次发送 API 前没有再次裁剪
- **修复**: 在 `while (toolRound <= MAX_TOOL_ROUNDS)` 循环内，每轮 API 调用前都执行 `trimHistoryIfNeeded()`

**问题 2**: 单次工具结果过大
- 一次 MCP 工具调用结果就可能有十几万字符，直接撑爆 token 限制
- **修复**: 将工具结果加入 `conversationHistory` 前自动截断，上限 30,000 字符
- 日志：`Tool result truncated: 393363 -> 30045 chars`

**问题 3**: `trimHistoryIfNeeded` 缺少兜底
- 如果裁剪完所有历史消息后仍然超限（比如 system + 最近一轮就超了），没有进一步手段
- **修复**: 添加两级兜底：
  1. 截断所有大于 5000 字符的 tool 消息到 3000 字符
  2. 最后手段：截断 system prompt 到 4000 字符

**问题 4**: 估算修正系数和安全余量
- 添加 1.3 倍修正系数弥补估算与实际 tokenizer 的差距
- 安全阈值 = `模型上下文限制 × 0.85 - 修正后的 tools token`

#### 5. 混元对齐 DeepSeek 的 MCP 支持
混元 HunyuanService 和 DeepSeek 使用相同的基类 `chatStream()` 方法，但之前缺少一些细节：

**修改内容**:
- 导入 `estimateToolsTokens`，日志对齐 DeepSeek 格式（显示 msgs/tools/total token 分布）
- 设置 `maxContextTokens = 32768`（混元 2.0 thinking 模型的上下文窗口）
- 流式请求加上 `stream_options: { include_usage: true }` 以获取 usage 信息

**新增 `maxContextTokens` 可配置属性**（`BaseAIService.ts`）:
- 基类默认 `maxContextTokens = 98304`
- DeepSeek 显式设置 `98304`
- 混元显式设置 `32768`
- `chatStream()` 中的安全阈值改为 `maxContextTokens × 0.85 - correctedToolsTokens`（不再硬编码）
